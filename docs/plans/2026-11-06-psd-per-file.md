# PSD 清理与每文件四路

## 用户修正

- 清理对象为 `.psd`，不是 `.pdf`；PDF 保留。修改开关、工作流阶段、统计、日志与指南。手动整理仍只移动，不删除任何文件内容。
- 每文件独立最多四路，文件级最多五个。账号限流暂停依旧共享；任何分片限流先发布账号等待再释放请求槽位，不通过新文件绕过。

## 实现约束

- 新清单只记录 PSD 删除项，执行前检查后缀。旧未完成自动清单保留已移动项目，剩余 PDF 加回移动清单；PSD 仅从该资源原清单与解压目录选取，不扫描其他根目录文件。
- 旧版实际已删除的 PDF 计数保留原义，并提示需从原包恢复，不伪装为新 PSD 计数。已完成旧资源不自动重新清理。
- 每文件局部请求槽位嵌套账号级槽位，局部初始四路、账号初始最多二十；服务端限流缩减额度并持久化账号等待。
- 根据 `help.getAppConfig` 下发的小/大文件队列上限按 DC 调度，保留用户五文件上限；读取失败走连接恢复，缺键明确记录。旧 CLI 不新增此要求。

## 依据与检查

- https://core.telegram.org/api/files：同 DC 文件队列限制及 FLOOD_WAIT/FLOOD_PREMIUM_WAIT。
- https://core.telegram.org/api/config#small_queue_max_active_operations_count：运行时配置来自 help.getAppConfig，不把文档示例的 5/2 写死。
- 检查源码、调用与差异，编译修改的 Python 模块并构建前端；沿用仅限独立数据的页面检查授权，不运行测试，不登录真实 Telegram，不实际移动或删除文件。
