# 下载吞吐优化

## 目标

- 用户反馈程序约 373.5 KB/s，而官方客户端同类下载可达 2–6 MB/s。优先优化程序，不修改用户代理。
- 网页提供 1 / 2 / 4 路分片并发，按用户最新选择默认上限 4 路；仍只处理一个文件。
- 文档附件使用 512 KiB 请求块，按实际文件大小分配互不重叠的区间；完整覆盖后才允许沿用原有完成、解压和删包流程。
- 遵守 FLOOD_WAIT / FLOOD_PREMIUM_WAIT：所有下载分片共同等待，降低有效并发，保留账号级等待期限，重启不跳过等待。
- 群进度回执不阻塞下载回调，保留发送节流与最终结果。

## 实现与边界

1. 新增 Telethon 公共 iter_download 路径；保留文档引用刷新、库标准 CDN 路径和照片原有下载方式。既有 CLI 调用不被要求提供新设置。
2. 增加下载等待状态、本次并发上限和页面设置；旧数据库通过默认设置兼容，不删除进度或会话。
3. 源码与调用关系自查、前端构建、独立页面检查；不新增或执行自动化测试，不登录真实 TG 或下载用户文件。
4. 按已有授权提交到 fork，跟进 GHCR 构建发布。真实吞吐由用户更新后对照同一文件确认，不承诺达到某个速度。

## 依据

- 已安装 Telethon 1.44：小于 100 MiB 的默认下载请求块为 128 KiB；下载过程逐块等待，进度回调也被等待。
- https://core.telegram.org/api/files
- https://docs.telethon.dev/en/stable/modules/client.html#telethon.client.downloads.DownloadMethods.iter_download

不新增多账号、换 IP 规避限制或跨文件批量并发，不恢复首次起点之前的旧消息。

## 实施记录

- 已接入默认 4 路、1/2/4 档位设置、512 KiB 分片、分片范围与大小检查，以及原有大小校验、fsync 和完成发布流程。
- 限流暂停在释放请求槽位前发布，下载分片共同等待；账号等待期限持久化，页面显示等待原因、恢复时间和本次并发上限。
- 群进度回执独立发送，保留串行更新与最终结果；CDN、照片走库的标准路径。
- 修改的 Python 模块语法编译、前端类型检查与生产构建完成。独立数据页面确认默认 4 路、切换并保存后刷新保留，以及限流等待状态显示；示例记录不作为真实下载证据。
- 未新增或运行自动化测试，未连接真实 TG 验证吞吐、分片重组或限流恢复；需要用户更新后以同一文件确认。
